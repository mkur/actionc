# TN 6502 Code-Generation Review

Review date: 2026-11-10.

## Scope and provenance

This document preserves the analysis of the user-supplied Action! assembly
listing for Tom's Navigator. It is a static review of the emitted listing, with
small exhaustive arithmetic checks. It is not an emulator benchmark, a
whole-program correctness proof, or a comparison against the original Action!
compiler.

| Input property | Value |
| --- | --- |
| Supplied filename | `Wklejony tekst.txt` |
| Listing header | Generated by actionc; re-originable MADS assembly listing |
| Runtime | `cart` |
| Original origin | `$2C00` |
| Input size | 297,750 bytes; 5,500 lines |
| Input SHA-256 | `9181a1e3bcd7f2ddf16de08b3103a1985cd5a933f6fe9f59cab98bd99c710d76` |
| Compiler revision, backend/profile, and source revision | Not established from the supplied listing |

All addresses below refer to that supplied listing. The listing was not
regenerated from the repository revision at which this review was saved.
Proposed replacements are optimization candidates, not changes implemented by
this document.

Byte savings are calculated from the emitted instructions. Cycle figures are
nominal NMOS 6502 timings, excluding Atari DMA and page-crossing penalties
unless stated otherwise. Instruction timings and flag behavior follow the
[MOS Technology MCS6500 Programming Manual, Appendix B (transcription)](https://lbaeza.neocities.org/mcs6500/6500_appb).
Arithmetic substitutions using `ADC` or `SBC` assume the compiler's normal
binary-arithmetic contract. Register, scratch-memory, and flag changes must
respect liveness and the applicable calling convention.

Savings for alternative or overlapping rewrites must not be added together.
In particular, removing `RemU8` after division/remainder fusion and replacing
it with a shared-core wrapper are alternatives.

## Overall conclusion

**This is competent code generation with several real optimizations already
present, but there is substantial room to improve how it handles temporary
values, pointers, and calls.** The strongest opportunities are in the string
and directory-processing code: values repeatedly move through memory even
when they could remain in registers or zero-page pointers.

The main recommendation is to strengthen **value tracking, callee clobber
analysis, and pointer allocation** before attempting a major backend redesign.
This listing contains several improvements that should be achievable through
relatively focused compiler passes.

There is also a possible correctness issue in `Quit` and a definite unresolved
symbol in the exported assembly listing. Those are discussed separately below.

## 1. Overall assessment

The main emitted segment occupies **9,956 bytes**, from `$2C00` through
`$52E3`. Approximately **8,209 bytes are in regions marked as generated
high-level code**, with another 114 bytes in the division helpers. The
remainder includes data and source assembly.

That distinction matters: `MovePage`, `CalcAdr`, `Internal`, `Block`,
`GetImage`, `PutImage`, and the CIO wrappers contain source assembly. Their
quality should not be credited to or blamed on the high-level code generator.
The menu definitions around `drives` and `density` are also data that the
listing has decoded as instructions.

| Area | Assessment |
| --- | --- |
| Basic instruction selection | Generally good: shifts, direct comparisons, compact increments |
| Tail calls and branch layout | Already reasonably well optimized |
| Register-value tracking | Useful optimization exists, but it is inconsistent |
| Temporary and parameter storage | Too much unnecessary movement through memory |
| Pointer and array handling | The largest recurring weakness |
| Loop generation | Correct-looking conservative structures, with considerable optimization potential |
| Arithmetic helpers | Byte specialization is good; duplication and missed arithmetic combinations remain |
| Exported assembly | Needs a code/data distinction and symbol validation |

### What is already good

Several things indicate that this is more than a straightforward
syntax-directed compiler.

- **Tail calls are used extensively.** Procedures such as `SavePos`,
  `RestorePos`, `Dir`, and `UpdDis` end with jumps to their final callee.
- **Small 16-bit increments are sensibly lowered.** There are many instances
  of incrementing the low byte and conditionally incrementing the high byte,
  rather than performing a full two-byte addition.
- **Multiplication by two and division by two use shifts.**
- **Some register contents survive across calls intelligently.** In generated
  `Putchar`, the character is kept in Y across `CalcAdr`. In other places, a
  known register value avoids an unnecessary reload.
- **Word-array indexing preserves the ninth bit of a doubled byte index.**
  Sequences involving `ASL` and `ADC #0` are sometimes necessary, even if they
  initially look verbose.
- **The obvious branch peepholes have largely been applied.** The review found
  no adjacent `JSR`/`RTS` pair, no jump to the immediately following
  instruction, and no simple branch-over-`JMP` pattern whose destination is
  already within relative-branch range.

Consequently, adding another generic "replace `JSR`/`RTS` with `JMP`" pass
is unlikely to make much difference to this particular output.

## 2. Eliminate unnecessary movement through temporary storage

This is the clearest class of inexpensive improvements.

### Strcpy: 16 bytes can become 4 bytes

At `$3860–$386F`:

```asm
TYA
STA $E2
LDA param_Strcpy_t+1
STA $E3
LDA $E2
STA $AC
LDA $E3
STA $AD
```

At this point:

- Y already contains the source pointer's low byte.
- A already contains its high byte, loaded at `$385B`.

The entire sequence can therefore become:

```asm
STY $AC
STA $AD
```

| Measure | Current | Improved |
| --- | ---: | ---: |
| Size | 16 bytes | 4 bytes |
| Cycles | 24 | 6 |

**Saving: 12 bytes and 18 cycles.**

This example is especially useful because it does not require a new calling
convention or a sophisticated loop transformation. It requires the backend to
remember which values are already in A and Y, and to eliminate dead scratch
copies.

The whole `Strcpy` procedure could be made considerably smaller by passing
its incoming values directly into the `MovePage` argument locations. However,
the local rewrite above is a better first compiler regression test because
it needs fewer assumptions.

### Several smaller examples show the same problem

| Location | Improvement | Saving |
| --- | --- | ---: |
| `Push`, `$2F5F` and `$2F65` | Remove `STX $E2`; replace the later `LDA $E2` with `TXA` | 3 bytes, 4 cycles |
| `Path`, `$3B71–$3B79` | Replace the temporary-based OR operation with `LDA global_drive / ORA #$30` | 4 bytes, 6 cycles |
| `PrintB`, `$4416–$441B` | Replace `STA $E2 / LDA #$30 / ORA $E2` with `ORA #$30` | 4 bytes, 6 cycles |
| `Sort`, `$3B27` and `$3B2E` | Remove two `LDY` instructions whose values are already in Y | 4 bytes, 4 cycles |

For example, the `Path` sequence is:

```asm
LDA global_drive
STA $E2
LDA #$30
ORA $E2
```

It can simply be:

```asm
LDA global_drive
ORA #$30
```

These patterns suggest that **expression lowering introduces temporary
locations which later optimization does not always remove**.

The compiler should track facts such as:

```text
A contains value v
X contains value w
Y contains value u
$E2 contains the same value as A
$AC/$AD contain pointer p
```

Stores should preserve relevant register facts. Reloads should be removed
when the value and required flags are already available.

## 3. Keep pointers live across calls and loop iterations

This is the most promising improvement for frequently executed code.

### SetWin: a particularly strong example

The character-conversion loop at `$41A4–$41DC` is **57 bytes**. Each iteration
does approximately this:

1. Copies `global_s` into two absolute spill locations.
2. Copies the index into another temporary.
3. Copies `global_s` into `$AC/$AD`.
4. Loads a character and calls `Internal`.
5. Restores the pointer from the spill locations.
6. Reloads the returned character from `$A0`.
7. Stores it and advances the index.

However, inspecting `Internal` shows that it:

- Changes A, X, Y, flags, and `$A0`.
- Leaves `$AC/$AD` untouched.
- Leaves `global_i` untouched.
- Returns the converted character in A as well as storing it in `$A0`.

Once the pointer is established, the loop can be:

```asm
        ; Set up once before the loop.
        LDA global_s
        STA $AC
        LDA global_s+1
        STA $AD

        ; Existing initialization: global_i = 2.

loop:
        LDY global_i
        LDA ($AC),Y
        JSR proc_Internal

        LDY global_i
        STA ($AC),Y

        INC global_i
        LDA global_i
        CMP #$0A
        BCC loop
```

This preserves the visible final value `global_i = 10`.

The comparison is substantial:

| Measure | Current loop | Improved loop |
| --- | ---: | ---: |
| Loop body | 57 bytes | 19 bytes |
| Caller cycles on an ordinary taken iteration | 89 | 36 |
| Including execution of `Internal` | 120 | 67 |

Adding a conservative one-time pointer setup costs 10 bytes and 14 cycles.
The result is still **28 fewer code bytes and 410 fewer cycles per
eight-character conversion**.

In fact, `$AC/$AD` already contain the desired pointer immediately before
this loop, so a sufficiently informed optimizer could save the extra setup
too.

This requires the normal aliasing condition: the directory-buffer writes must
not overwrite `global_s` or reserved compiler scratch. The compiler should
establish that from its memory model, rather than assume it for arbitrary
pointers.

**This is the first example to turn into a compiler optimization test.** It
combines register tracking, pointer tracking, return-value knowledge, and call
effects in a short, meaningful loop.

### Fnamecmp: pointer promotion could nearly halve the ordinary loop cost

The equal-character loop at `$3A21–$3A4F` repeatedly copies two pointers from
absolute parameter storage into zero page:

```asm
LDA param_Fnamecmp_s
STA $AE
LDA param_Fnamecmp_s+1
STA $AF

LDA param_Fnamecmp_t
STA $AC
LDA param_Fnamecmp_t+1
STA $AD
```

It then compares characters and increments the pointers in their absolute
parameter locations.

There are **no calls inside this loop**. If those parameter locations do not
escape, the pointers can live in zero page throughout the comparison.

For the same basic loop structure:

- Current: approximately **63 cycles per equal character**.
- Pointers retained and advanced in zero page: approximately **33 cycles**.

Those figures assume neither pointer's low byte wraps during that iteration.

Using Y as a shared offset could reduce ordinary iterations further, but then
the compiler must handle Y wrapping and preserve any required final pointer
values. Pointer promotion alone is already a worthwhile improvement.

### The same opportunity appears elsewhere

`Print`, `PrintFname`, `Instr`, and `Convert` repeatedly reconstruct pointers
that are often unchanged.

For `Print`, it is reasonable to retain the pointer across `Putchar` after
accounting for the complete `Putchar -> CalcAdr/Internal` call chain. The
compiler already has some call knowledge; the opportunity is to make that
knowledge consistently available to allocation and load elimination.

A useful function summary should describe:

- Registers modified.
- Zero-page locations modified.
- Other memory read or written.
- Whether the function can return.
- Where its result remains.
- Which flags describe that result.

For inspectable assembly, these facts can sometimes be derived. `ASM OPAQUE`
needs a conservative treatment or explicit declarations.

## 4. Improve addressing-mode selection and use proven ranges

Some address calculations are more elaborate than the 6502 requires.

### Fold constant offsets into indexed operands

In `Init`, `$380A–$3815` calculates `i + 24` explicitly before storing the
high byte of a lookup-table entry:

```asm
LDA global_i
CLC
ADC #$18
TAY
LDA local_Init_h+1
STA global_quickmul,Y
```

But Y already contains `i` from the preceding store. The code can be:

```asm
LDA local_Init_h+1
STA global_quickmul+24,Y
```

**Saving: 6 bytes and 9 cycles per iteration.**

The loop establishes `i < 24`, so there is no ambiguity from eight-bit index
overflow.

This should be a general addressing-mode optimization: where semantics permit
it, fold a constant into the base address instead of computing it in A.

### Use conditions to simplify subsequent address arithmetic

In `Handle`, the code at `$4EEC` checks:

```asm
LDA global_active+1
CMP #4
BCC loc_Handle_10
```

On arrival at `loc_Handle_10`, A is known to be in the range 0–3.
Nevertheless, the following address calculation preserves the possible ninth
bit of `A * 2` with `PHP` and `PLP`:

```asm
ASL
PHP
CLC
ADC global_dirsectors
STA $AA
LDA #0
ROL
PLP
ADC global_dirsectors+1
STA $AB
```

Because the preceding branch proves that `ASL` cannot set carry, this can
become:

```asm
ASL
ADC global_dirsectors
STA $AA
LDA global_dirsectors+1
ADC #0
STA $AB
```

**Saving: 4 bytes and 11 cycles.**

There is a similar case in `Sort`: after excluding values at or above `$80`,
the carry from doubling the remaining index is necessarily zero, making the
`ADC #0` at `$3A8E` unnecessary.

The qualification is important: **the general word-array indexing sequence
is valid and sometimes necessary**. The optimization comes from a proven
range, not from assuming that all array indices are small.

## 5. Improve arithmetic lowering

There are three distinct opportunities here.

### A. Multiplication by 20 should be strength-reduced

There are three calls to `MultI` at `$A000`:

- `Window`, `$3277`: a variable dimension product.
- `DrawWinFrame`, `$3C98`: multiplication by 20.
- `SwapWin`, `$43CA`: multiplication by 20.

The latter two only consume the low byte of the result. This sequence computes
that byte for every possible byte input:

```asm
LDA global_winnum
ASL
ASL
STA tmp             ; 4 * winnum, modulo 256
ASL
ASL                 ; 16 * winnum, modulo 256
CLC
ADC tmp             ; 20 * winnum, modulo 256
```

With a zero-page temporary, this is **12 bytes and 20 cycles**, before storing
the result.

The existing setup and call occupy **16 bytes** and already take **22 cycles
before execution inside `MultI`**.

This improvement combines:

- Constant multiplication strength reduction.
- Recognition that only the low eight result bits are needed.

It does not depend on assuming that `winnum` is always 0 or 1.

The variable multiplication in `Window` is a different case. A runtime helper
is a reasonable choice there unless the compiler has additional bounds or a
better costed multiplication implementation.

### B. Combine quotient and remainder calculations

`PrintB` computes `b / 100` at `$43E0`, then recomputes the division to obtain
`b % 100` at `$43EA`.

Yet `DivU8` already leaves:

- Quotient in `$82` and A.
- Remainder in `$86`.

Thus:

```asm
JSR proc_actionc_DivU8
STA global_i

LDA param_PrintB_b
LDX #100
JSR proc_actionc_RemU8
STA param_PrintB_b
```

can become:

```asm
JSR proc_actionc_DivU8
STA global_i

LDA $86
STA param_PrintB_b
```

The replacement saves **6 bytes and approximately 246–261 cycles**, using
the existing division implementation.

The `/10` and `%10` operations later in `PrintB` are another pair. There is a
conditional `Putchar` between them, so either retain the remainder using the
callee summary or save it before the call.

**These are the only two `RemU8` call sites in the listing.** After combining
both pairs, the entire 57-byte remainder helper becomes unnecessary.

At the IR level, this argues for an operation with two outputs:

```text
quotient, remainder = unsigned_divmod(numerator, denominator)
```

Division and remainder with identical operands can then share the calculation.

For a different program that genuinely needs both entry points independently,
a size-oriented alternative is a shared division core with a small remainder
wrapper. The current two helpers occupy 114 bytes; retaining the 57-byte
divider plus a six-byte wrapper would use 63 bytes, at the expense of an extra
call/return for remainder operations. That is an alternative saving, not
something to add to the helper removal above.

### C. The byte-division core itself can improve

The current helpers rotate the partial remainder in memory, then repeatedly
reload it.

For strictly eight-bit division, with an initially zero remainder and eight
iterations, the partial remainder can instead remain in A:

```asm
        ; Existing entry and divide-by-zero handling retained.
        ; $82 = numerator, $84 = divisor.

        LDA #0
        LDX #8
loop:
        ASL $82
        ROL
        CMP $84
        BCC next

        SBC $84             ; CMP already established C = 1
        INC $82
next:
        DEX
        BNE loop

        STA $86             ; remainder
        LDA $82             ; quotient
        RTS
```

The existing `BCS` after rotating the memory remainder is unnecessary for
this particular 8/8 algorithm: the partial remainder cannot overflow the
byte during those eight iterations.

The arithmetic was checked exhaustively for **all 65,280 combinations of
byte numerator and nonzero byte divisor**. With the existing entry and error
handling retained, this reduces a helper from **57 to 47 bytes** and saves
**64–128 cycles per division**, depending on the quotient.

Constant division provides another opportunity. For `/100` on a byte, the
quotient can only be 0, 1, or 2. A specialized comparison/subtraction sequence
can exploit that. After `%100`, the next numerator is known to be below 100,
which also helps `/10`.

These are useful compiler improvements, though decimal printing is unlikely
to determine the application's overall responsiveness.

## 6. Preserve values and condition flags across branches

The control-flow layout is fairly good. The missed opportunities are often
in the information passed between blocks.

### Draw recomputes a value that remains in A

The prefix at `$3BB1–$3BD0` computes the smaller of:

```text
(cnt + 16) modulo 256
global_active
```

One arm calculates `cnt + 16` again, although A still contained it at the
comparison.

The 32-byte prefix can become:

```asm
STA param_Draw_cnt
CLC
ADC #$10
CMP global_active
BCC store_result
LDA global_active

store_result:
STA global_r0
```

This is **16 bytes**, saving **16 bytes and 9–12 cycles**.

It preserves the existing eight-bit wraparound behavior; it does not silently
turn the addition into a wider one.

### Fnamecmp can return the comparison already held in carry

The loop exits through:

```asm
LDA ($AE),Y
CMP ($AC),Y
BNE loc_Fnamecmp_9
```

At that destination, the characters are unequal and carry already indicates
their ordering.

Nevertheless, the generated suffix reloads both characters, compares them in
the reverse order, and selects zero or one.

For the visible caller and its return-value contract, the suffix can be:

```asm
LDA #0
ROL
STA $A0
RTS
```

This changes **18 bytes into 6 bytes**, saving **12–13 nominal cycles** as
well as the eliminated indirect-read page penalties.

The essential optimization is to retain the meaning of carry across the
taken branch. This rewrite assumes ordinary RAM and permits changes to
return flags that are dead under the caller's contract.

### Handle repeats a comparison in reverse

At `$4FEE`:

```asm
LDA local_Handle_d
CMP global_active+4
BCS loc_Handle_16
```

Arrival at `loc_Handle_16` proves `old >= new`. It then loads the operands in
reverse and checks `new >= old`.

Under the established condition, that means equality, already represented by
Z. The three instructions at `$5006–$500C` can become:

```asm
BEQ loc_Handle_18
```

**Saving: 6 bytes and 8 cycles.**

### Re-run branch relaxation after shrinking code

`Range` contains redundant pointer loads, repeated `LDY #0`, and carry
initialization on paths where carry is already known.

Removing 14 bytes of these instructions also brings a backward branch into
relative range. That permits another three-byte saving by replacing a
branch-over-jump sequence.

This is a useful implementation detail: **branch relaxation should run after
the instruction simplifications have reached a stable result**. A branch
that is necessarily long in the reviewed output may become short after
other optimizations.

## 7. Be careful with loop simplifications

The repeated sequence:

```asm
LDA index
CMP #$FF
BCS exit
INC index
JMP test
```

looks cumbersome, but it prevents an inclusive byte loop from wrapping at
255.

Replacing it mechanically with:

```asm
INC index
BNE loop
```

can change the final index value from `$FF` to `$00`, and can also change
termination behavior.

The right improvements are conditional:

- Remove overflow protection when the bound is proven below 255.
- Keep indices in registers when calls, aliasing, and final-variable semantics
  permit it.
- Hoist stable pointer setup and bounds.
- Rotate loops while preserving zero-trip behavior.
- Use a running pointer or offset when it reduces repeated address calculation.

The listing already generates tighter constant-bound loops in places such as
`SetWin` and `Convert`. Extending the range information available to the
backend should help the more conservative cases.

Also, static local storage cannot be treated as universally disposable.
Variables such as `local_InitPanels_times`, `local_Format_last`, and
`local_SwapScr_firstTime` intentionally preserve state between calls.
Parameter or local storage elimination needs escape and lifetime analysis.

## 8. Issues to check separately from optimization

### A. Quit does not read back $BFFA

At `$4DBA–$4DC6`:

```asm
LDA $BFFA
STA global_i
EOR #$FF
STA $BFFA
CMP global_i
BNE loc_Quit_1
```

The branch compares the complemented value still in A with the original byte.

For every byte `x`:

```text
(x XOR $FF) != x
```

Therefore, in ordinary execution, the branch is always taken.

**If this is intended as a RAM-versus-ROM write probe, it cannot work as
emitted**, because the code never reads `$BFFA` after the store. Such a probe
needs a real readback:

```asm
STA $BFFA
LDA $BFFA
CMP global_i
```

The Action! source is needed to determine the cause. Possibilities include a
missing volatile declaration, an optimization that improperly forwarded a
stored value, or source code that never requested the readback.

This should be investigated before constant-folding the branch away.
Fixed-address objects used for hardware or ROM probing need appropriately
defined observable-access semantics.

### B. PrintB appears to omit an interior zero digit

The tens digit is suppressed whenever it is zero, even after the hundreds
digit was printed.

The visible behavior would therefore include:

| Input | Output |
| ---: | --- |
| 100 | `10` |
| 101 | `11` |
| 200 | `20` |
| 110 | `110` |

That looks like a formatting defect, but **it is not evidence of a compiler
bug without the source**. It may faithfully implement the source logic.

It is nevertheless a useful regression case when changing the division
code: distinguish preserving current behavior from correcting the formatter.

### C. The exported listing contains an undefined symbol

At `$445E`:

```asm
ADC.A loc_drives_10
```

`loc_drives_10` has no definition in the supplied file.

This occurs in menu data decoded as instructions. The intended address,
`$445B`, falls inside a previously decoded instruction, which is consistent
with a disassembler losing the data boundaries.

For the exporter:

- Preserve known data as `.BYTE`, `.WORD`, or appropriate MADS data directives.
- Preserve relocation information for embedded addresses.
- Validate that all emitted symbolic references resolve.
- Check reassembly at the original origin and at a different origin.

This is a defect in the supplied assembly export, distinct from the quality
of the original executable.

## 9. Suggested compiler-development priorities

| Priority | Improvement | Best examples from this listing |
| --- | --- | --- |
| 1 | Register and zero-page value tracking; redundant-copy elimination | `Strcpy`, `Push`, `Path`, `Sort` |
| 2 | Precise callee effects and result-location summaries | `SetWin` calls to `Internal` |
| 3 | Pointer promotion and loop-invariant setup | `Fnamecmp`, `Print`, `Instr`, `Convert` |
| 4 | Branch-derived facts and flag tracking | `Draw`, `Handle`, `Range`, `Fnamecmp` |
| 5 | Arithmetic combination and demanded-width analysis | `PrintB`, multiplication by 20 |
| 6 | Costed dispatch and selective inlining | `MakeJmp`, small leaf functions |

`MakeJmp` is a reasonable later target: its nine consecutive cases occupy
64 bytes as a comparison chain. A bounds-checked jump-table implementation
can be smaller and improve the late-case dispatch time. The early cases may
be faster with the present chain, however, and this is an interactive command
path, so it belongs behind the string-processing improvements.

For verification, retain small regression examples covering the demonstrated
transformations, with special attention to byte values 0, 127, 128, 254, and
255; pointer page crossings; aliasing; required readbacks; and return-register
assumptions.

**The most valuable next step is to make the backend keep values where they
are already useful.** The `Strcpy` and `SetWin` examples show that considerable
waste comes from losing knowledge during lowering: the desired pointer or
result is already available, but the generated code stores, reconstructs,
and reloads it. Fixing that consistently should improve both code size and
execution time across many Action! programs.

## Repository integration notes

Implementation should follow the ownership and safety rules in
[AGENTS.md](../AGENTS.md): source-language semantics belong to SemIR;
normalized typed computation and conservative effects belong to verified
NIR; target addressing, registers, flags, zero-page placement, helper
selection, and target peepholes belong to MIR6502; labels, data writing,
relocations, and listing validation belong to emission. Proposed optimizations
must use structured facts and general compiler behavior, not special cases
for TN.
